# Database

PostgreSQL (local Supabase CLI stack; the hosted DB in deploys) with Drizzle ORM. Schema defined in `server/services/drizzle/schema.ts`. Connection via the `node-postgres` (`pg`) driver.

## `useDrizzle()`

Singleton accessor from `server/utils/drizzle.ts`. Auto-imported in server context.

```ts
const [trip] = await useDrizzle().select().from(tripsTable).where(eq(tripsTable.id, tripId))
```

Reads `NUXT_DATABASE_URL` via `useRuntimeConfig()`. One `pg` `Pool` is reused across requests.

## Schema Conventions

- `snake_case` table/column naming via `casing: 'snake_case'` (in `drizzle.config.ts` and the drizzle client) — do NOT specify explicit column names
- UUID primary keys generated by PostgreSQL (`uuid().primaryKey().defaultRandom()`). Trip ids appear in WhatsApp links, so they must stay random — never serial ids on anything a URL exposes
- Never use `pgEnum` for fields like `status`, `kind`, `domain` — use plain `varchar` and validate at the Zod schema level only. Easier to evolve, no migration churn for adding a value
- Ordered children (days in a trip, items in a day) carry an explicit integer `position` — never rely on insert order or `created_at`
- Knowledge-graph tables (people, preferences/constraints) are separate from trip tables. A trip may reference the traveller; the plan never copies preference values into trip rows
- For columns computed from sibling columns, use `.generatedAlwaysAs(sql\`…\`)` — not triggers or application-layer fallback

## Migrations

- Always generate via `pnpm db:migration:generate` — never write migration SQL by hand
- Manual edits only acceptable for operations Drizzle doesn't generate (e.g., `CREATE EXTENSION`, DML `INSERT INTO`)
- Review generated SQL in `drizzle-out/` before applying (`pnpm db:start` / `pnpm db:reset` locally, `pnpm db:migration:run` in deploy)
- Commit migration SQL alongside the schema change in the same PR
- Migrations run after the build in `.github/workflows/deploy.yml` — keep them backward-compatible with the previous deploy

## Seed

The only seed is the stay/place/transport catalogue, `supabase/seed/catalogue.sql`, applied after migrations on `supabase start` / `pnpm db:reset`. It is generated — deterministically, from a fixed PRNG seed — by `buildCatalogue` (`server/controllers/catalogue/buildCatalogue/`, city data in `catalogueCities.ts` with real GeoNames ids — the ones the city picker returns), written to SQL by `supabase/seed/catalogue/generate-catalogue.ts`; run `pnpm db:catalogue:generate` and commit both. The builder keeps relative imports only, so the script runs under plain tsx. Deployed databases are seeded with the same builder through `POST /api/catalogue/seed` (upsert by ref, gated by `NUXT_CATALOGUE_SEED_ENABLED`). Attribute shapes must match `server/types/catalogue/` and stay within `RULE_FIELDS`, or compiled rules can't evaluate them. No users or trips are seeded; never seed a `queued`/`running` run (boot recovery would re-send its job and start a real agent run).

## Prefer Drizzle DSL

Use Drizzle index builders (e.g., `.unique()`, `.index()`) rather than raw `sql` strings wherever possible. `.$default()` is JavaScript-level only and cannot reference sibling columns — use `.generatedAlwaysAs(sql\`…\`)` for that.

## Naming

| Element | Convention |
|---|---|
| Table file export | `tripsTable`, `tripDaysTable`, `tripItemsTable`, `preferencesTable` (always `*Table` suffix) |
| Column name | `snake_case` in DB, `camelCase` in TS (automatic via `casing: 'snake_case'`) |
| Index | `<table>_<columns>_idx` |
| Unique | `<table>_<columns>_unique` |
| Foreign key | inferred — don't name explicitly unless needed |

## Connection Pooling

`NUXT_DATABASE_URL` must be a direct or **session-mode** connection, never the transaction pooler (port 6543): pg-boss (LISTEN/NOTIFY, advisory locks) and the LangGraph checkpointer need sessions the transaction pooler doesn't keep. Three pools share it — Drizzle, pg-boss, the checkpointer. Locally it is the direct connection (`127.0.0.1:56322`). pg-boss owns schema `pgboss` and the checkpointer `langgraph`; both create themselves on server start and are not Drizzle-managed (`schemaFilter: ['public']`). The pool's `error` listener in `server/utils/drizzle.ts` must stay: without it an idle client dropped by the pooler crashes the instance.
